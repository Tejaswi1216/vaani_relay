# The Relay: Technical Report and Operational Analysis

## 1 What I built and why

"The Relay" is an asynchronous multi-stage question-answering pipeline that queries three foundational research papers (`attention_v7` [arXiv:1706.03762v7], `moshi_v1` [arXiv:2410.00037v1], and `dynchunk_v2` [arXiv:2507.07955v2]) using Groq's free-tier API (`qwen/qwen3.8-27b`) and a calibrated FastAPI stand-in model service.

Operating production LLM pipelines under free-tier constraints introduces a fundamental tension: user expectations demand fast, interactive responses, but strict upstream rate limits (30 RPM, 8,000 TPM, 1,000 RPD, 200,000 TPD) turn concurrent requests into catastrophic failure cascades. Naive retry loops exacerbate congestion via the thundering herd problem, while blind streaming violates answer fidelity by emitting hallucinations before verification completes.

To resolve this, I implemented:
1. **A 5-Step Pipeline** (`relay/pipeline.py`): (1) question classification and paper targeting; (2) BM25 passage retrieval; (3) evidence adequacy evaluation (branching to refuse or widen retrieval); (4) model drafting with tight token bounds (`max_tokens=220`); and (5) deterministic quote-in-source citation verification.
2. **Shaping Decision 1: Dual-Leaky-Bucket Admission Control** (`relay/policy.py`): A client-side admission controller tracking local TPM and TPD capacity. If queuing delay exceeds `PATIENCE_TTFT_MS` (8,000 ms), the request is shed early with HTTP 429 rather than queueing into an upstream timeout.
3. **Internal Buffering with Verified Flush** (`relay/pipeline.py` lines 185–201): In strict compliance with Rule R7 ("never send a wrong or embarrassing answer to stay fast"), tokens generated by the model are buffered internally during verification. If cited quotes are not verified against the source text, the draft is purged and replaced with an honest refusal.

## 4 Where the time goes

Diagnostic breakdown with `scripts/explain_slow.py` reveals how total latency decomposes across pipeline stages:
- **Zero-Load Baseline:** Under uncontended execution (`real_steady`), requests average 1,352.5 ms total time. Client connection and prompt transport account for ~400–600 ms, model decode accounts for ~120–150 ms (at ~1,660 tokens/s), and local deterministic verification takes < 5 ms.
- **Congested Load Breakdown:** On slow requests (e.g., `steady_0005_a685cb`, total time 27,249 ms, documented in `docs/slow_request_explanation.txt`), latency is dominated by:
  - **Waiting time:** 26,177 ms (96.1% of total time), split between admission queue waiting (21,500 ms) and backoff sleep (4,677 ms).
  - **Working time:** 1,072 ms (3.9% of total time) spent in actual model generation.
  - **First-token placement:** Delay occurs entirely **before the first token** because internal buffering holds tokens until verification succeeds. Once verification completes, verified tokens flush instantaneously.

## 5 When a limit is hit

Token limits bind far before request limits. With an average prompt size of ~1,800 tokens and 200 output tokens (~2,000 tokens total), the 8,000 TPM limit accommodates only **3.3 concurrent requests per minute**, despite the 30 RPM ceiling.

When the TPM or RPM bucket is exhausted:
1. Groq returns `HTTP 429 Too Many Requests` with header `retry-after: 2` and JSON payload `{"error": {"message": "Rate limit reached for model ...", "type": "tokens"}}`.
2. Recovery window is sharp: after 2.49 seconds of silence, the bucket refills and subsequent requests succeed immediately.
3. Under our Dual-Leaky-Bucket Admission Control, excess traffic is shed locally in < 1 ms with status `rate_limited`. In `burst` (stand-in, 150 requests), 91.3% were shed immediately, preserving server sanity and avoiding wasted upstream timeouts.

## How this library will mislead a naive retriever

Offline analysis (`docs/misleading_retrieval.md`) identified three concrete library failure modes:
1. **Jargon Saturation without Definition (`q07`, `moshi_v1`):** Moshi mentions "Helium" 47 times across 15 pages in passing (e.g. "We initialize from Helium..."). A naive BM25 query retrieves architectural comparisons rather than page 3, which contains the only explicit training definition (7B parameters, 2.1T tokens).
2. **Formula Extraction Degradation (`q01`, `attention_v7`):** Mathematical expressions like $\text{softmax}(QK^T / \sqrt{d_k})V$ extract as Unicode fragments (`QK T / √dk`). Exact string matching fails unless the retriever and verifier normalize math operators and whitespace.
3. **Trap Vocabulary & Distractor Baselines (`q20`, `dynchunk_v2`):** Queries about H-Net's heuristic-free boundaries match Section 5 baseline comparisons that repeatedly discuss external heuristics, causing naive retrievers to return the wrong model's parameters.

## 6 Retries

Under sustained overload (60 requests at 2x capacity), I compared our jittered exponential backoff policy (honouring `retry-after`) against a naive retry policy (immediate retry, 5 attempts, ignoring `retry-after`), documented in `docs/retry_experiment.md`:
- **Naive Policy:** Resulted in an immediate thundering herd. It generated **3.33 retries/request**, achieved only **16.7% success**, and produced an **83.3% rate-limited failure rate**.
- **Our Policy:** Exponential backoff with jitter and `retry-after` honouring reduced retries to **2.45 retries/request** and achieved **20.0% success** (a 20% relative throughput improvement), with 68.3% shed early by admission control.
- **Where retrying made things worse:** Retrying during continuous overload worsened upstream queue collapse; without client-side admission shedding, 100% of retried requests timed out.

## 7 What the person sees

At 3:00 PM when the 200k daily token budget is exhausted:
1. The user enters a question.
2. The Dual-Leaky-Bucket Admission Controller immediately detects `tpd_bucket < token_reservation` without making any upstream network call.
3. In `relay/pipeline.py` lines 128–135, the admission check rejects the request:
   ```python
   # relay/pipeline.py:131-135
   record.status = "rate_limited"
   record.total_ms = total_ms
   record.raw_response_text = f"HTTP 429: {reason}"
   ```
4. The user receives the exact response text:
   > `"HTTP 429: Daily token budget exhausted (deficit=2450)"`
5. Latency is under 1 ms; no quota is wasted, and the user is provided an honest status rather than an indefinite spinner.
